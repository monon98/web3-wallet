# 文件大小与拆分（>400 行尽量拆分）

当单个源码文件（`.ts` / `.tsx` / `.js` / `.jsx`）**超过 400 行**时，优先考虑拆分为多个更小、更单一职责的模块，以提升可读性、可维护性与代码评审效率。

## 规则

- **阈值**：超过 **400 行**视为“需要拆分”的信号（不是硬性禁止，但默认要行动）。
- **最小改动**：拆分应服务于职责边界与可读性，避免“顺手重构”导致 diff 失控。
- **保持入口稳定**：对外 API / 组件尽量保持原导出路径不变；必要时通过 `index.ts` 聚合导出。

## 优先拆分方式（从低风险到高收益）

- **抽 helpers**：将纯函数与工具逻辑移动到同目录 `*Helpers.ts` / `utils/*.ts`。
- **抽 types**：把类型定义移动到 `src/types/*.ts`（各子项目按既有约定，如扩展用 `apps/extension/src/extension/types/` + `index.ts` 聚合）。
- **抽常量与 schema**：常量、Zod schema、映射表独立到 `constants.ts` / `schemas.ts`。
- **UI 拆组件**：大组件拆为 `components/` 子组件 + `hooks/` 自定义 hooks；保持容器组件负责组合与数据流。

## 允许的例外（可以不拆）

- **工具链/配置/生成物**：如 `eslint.config.*`、`tsconfig.*`、`.d.ts`、自动生成代码。
- **框架强约定入口**：框架/平台要求单文件入口且拆分会破坏构建或约定时。
- **文档与测试夹具**：可读性优先，不强制按 400 行拆分。
